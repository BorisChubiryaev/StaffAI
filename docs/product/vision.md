# Видение продукта StaffAI

> Синтез из [Видения продукта](../sources/05-product-vision.md), [ТЗ v3](../sources/01-tz-v3-mvp.md) §1–4 и
> [Замечаний](../sources/legacy/remarks-collaborative-spec.md). При изменении первоисточников обновляйте этот документ.

## Видение одной фразой

**Владелец продукта описывает потребность в ИТ-специалистах один раз, простым языком — а StaffAI превращает её в проверенный
заказ, проект спецификации и данные для ЗНР, оставляя все значимые решения за человеком.**

«Сказал — получил»: заказчик говорит, система делает, штаб решает.

## Elevator pitch

Для **владельцев продуктов и лидеров команд банка**, которым срочно нужны внешние ИТ-специалисты,
и для **сотрудников штаба**, которые оформляют такие заказы,
**StaffAI** — это внутренний веб-сервис с AI-агентом (GigaChat), который
принимает запрос в свободной форме, уточняет его, проверяет по договорам и справочникам, готовит проект спецификации
и данные для ЗНР без повторного ввода.
**В отличие от** веб-форм и генераторов документов, StaffAI — операционный слой сквозного процесса: диалог вместо формы,
данные вводятся один раз, выводы AI объяснимы, а решения принимает человек.

## Проблема

| Сейчас | Последствие |
|---|---|
| Заказчик должен знать номера договоров, бюджетные коды, CI, правила спецификаций и формат ЗНР | Это не его зона ответственности — ошибки, задержки, раздражение |
| Одни и те же данные вводятся 3–4 раза: заявка → спецификация → трекер → ЛК | Трудозатраты и расхождения между артефактами |
| Цикл от обращения до готовой заявки — **недели** ручных итераций | Специалисты выходят поздно, план разработки срывается |
| Статусы непрозрачны | Заказчик не знает, где заявка; штаб тратит время на ответы «как дела» |
| Штаб получает неструктурированные запросы и собирает недостающее вручную | Штаб — узкое место; процесс зависит от памяти конкретных людей |

Без продукта процесс остаётся ручным, а смежные команды продолжают строить точечные решения без сквозного процесса.

## Для кого

| Сегмент | Кто | Что ценит | Роль в системе |
|---|---|---|---|
| **Заказчик ресурсов** (ключевой) | Владельцы продуктов, лидеры трайбов/команд, PM блока B2C и смежных | Скорость вывода специалистов, минимум бюрократии | Заказчик |
| **Сотрудник штаба** | Операционные сотрудники, управляющие привлечением | Предпроверенная карточка вместо «сырого» запроса, меньше рутины | Исполнитель |
| **Администратор** | Сопровождение системы | Управляемые шаблоны, справочники, доступы, журналы | Администратор |
| Опосредованно | Подрядчики (получают проект спецификации по почте), руководители (метрики) | — | Вне системы / отчёты |

Пилот — ограниченная группа заказчиков блока B2C; периметр масштабирования — открытый вопрос.

## Ценность

- **Заказчику:** описал потребность один раз в диалоге → подтвердил карточку → видит статус. Никаких договоров, ставок, CI.
- **Штабу:** на входе — карточка с анализом AI (уверенность, источники, противоречия, флаги бюджета/договора) и варианты
  подрядчиков; проект спецификации генерируется, штаб верифицирует и решает.
- **Банку:** быстрее вывод ресурсов, стандартизированный процесс (единое окно), полный аудит, основа для дальнейшей
  автоматизации контрактного контура.

## Продуктовые принципы

Это «характер» продукта. Нормативная, проверяемая форма — в [конституции](../../.specify/memory/constitution.md).

1. **Цель — специалисты в команде, а не документ.** Спецификация, ЗНР, пакет для трекера — downstream-артефакты.
2. **Заказчик — не оператор бэк-офиса.** Он не выбирает договор, не вводит бюджетные коды, CI, ставки, этапы.
3. **Диалог вместо формы.** Основной путь — разговор с агентом; формы — только для подтверждения и правки.
4. **Один ввод — многократное использование.** Данные вводятся один раз и переиспользуются во всех артефактах.
5. **Решение — за человеком.** AI рекомендует; выбор подрядчика, бюджет, отправка на согласование — за исполнителем.
6. **Объяснимость.** Каждый вывод AI — с уверенностью и источником; факт, справочник и предположение разделены.
7. **Модель не выдумывает.** Договоры, ставки, CI, бюджет — только из систем-источников; иначе «не найдено».
8. **Критический путь без искусственных блокеров.** То, что можно уточнить позже, не останавливает заявку.
9. **Устойчивость.** Недоступность GigaChat или внешней системы не останавливает процесс — деградация, а не отказ.

## Чем StaffAI не является

- ❌ Веб-формой / заменой Excel / «collaborative form filling»
- ❌ Генератором DOCX/PDF
- ❌ Автономным агентом, который сам выбирает подрядчика, утверждает бюджет или подписывает документы
- ❌ Источником истины для договоров, ставок, справочников (источник — КАП и справочники)
- ❌ Системой оплаты, учёта НМА, согласования в действующих системах, сопровождения выполнения работ (вне периметра)

## Как поймём, что получилось

Все цифры — целевые; базовая линия замеряется штабом до пилота.

| Цель (ТЗ §2.2) | Сейчас | Цель |
|---|---|---|
| Ц1. Время до структурированного проверенного запроса | дни–недели | минуты–часы |
| Полный цикл до ЗНР | недели | сокращение в ≥2 раза (подтверждается на пилоте) |
| Ц2. Повторный ввод данных | 3–4 раза | один раз |
| Ц3. Первичный разбор заявки штабом | ручной сбор | разбор предпроверенной карточки за минуты |
| Ц4. Прозрачность | нет единого статуса | статус на каждом шаге для заказчика и штаба |
| Ц5. Аудируемость | — | полный журнал событий, решений и версий |

Качество AI: точность извлечения на эталонном наборе ≥ согласованного порога, доля ручных корректировок, инциденты
недостоверной генерации — см. [метрики](scope-mvp.md#метрики).

## Горизонты

| Горизонт | Что | Статус |
|---|---|---|
| **Этап 1 — MVP** (этот проект) | Приём заявки в диалоге → уточнение → проверка и валидация → карточка → штаб → подрядчик → проект спецификации → решение → рассылка на согласование → пакеты для ЛК и трекера | В разработку |
| Этап 2 | Проверка артефактов выполнения, подготовка запуска оплаты; автосоздание Epic/Story; FinAI | После Этапа 1 |
| Целевая АС | Оплата, учёт НМА — при миграции | Вне периметра |
| Перспектива | Библиотека знаний (Confluence), Пульс ЕК, ServiceManager, COST IT, автоотправка на согласование по метрикам качества | Требует проработки |
