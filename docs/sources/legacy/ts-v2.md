## Executive Summary

### 0.1 Назначение версии v2.0

Данная версия ТЗ является полноценной переработкой исходной спецификации v1.0. Базовая логика исходника сохранена: AI-first сбор запроса, шаблоны, интерфейс заказчика, интерфейс штаба, интеграции, требования к AI-агенту, data model, NFR, метрики и фазирование.

Ключевое изменение версии v2.0: система позиционируется не как web-форма для подготовки спецификации, а как **AI-assisted operational workflow platform** для end-to-end процесса привлечения внешних IT-специалистов.

Спецификация, backlog, карточки Jira/SberTrack, конфигурационные файлы, сопроводительные документы и расчёты являются downstream-артефактами. Они важны, но не являются конечной ценностью продукта.

Конечная ценность продукта — более быстрый, прозрачный и управляемый вывод внешних специалистов в команды заказчиков при меньшей нагрузке на заказчика и штаб.

### 0.2 Главная продуктовая рамка

Система решает не задачу “сформировать спецификацию”, а задачу:

> помочь заказчику сформулировать потребность в IT-специалистах, преобразовать её в структурированный запрос, обогатить справочными данными, передать штабу для верификации, подготовить необходимые downstream-артефакты и сопровождать процесс до фактического вывода специалистов.

Именно поэтому система должна строиться вокруг workflow привлечения ресурсов, а не вокруг документа.

### 0.3 Ключевые изменения относительно v1.0

В v2.0 добавлены и уточнены следующие элементы:

- разделение **Product Vision / MVP / Target State**;
- explicit **Request Lifecycle / State Machine**;
- архитектурная декомпозиция на **bounded contexts**;
- разделение **LLM logic** и **deterministic business logic**;
- **AI Governance** и anti-hallucination rules;
- human-in-the-loop модель;
- target operating model для заказчика, AI-агента и штаба;
- расширенная data model;
- event model;
- уточнённая стратегия Vercel demo / prototype;
- out-of-scope для demo и MVP;
- acceptance criteria для prototype и MVP;
- риски реализации и способы их снижения.

### 0.4 Что критично не повторить из текущего demo-приложения

Текущий demo-подход с collaborative form filling не должен стать основой целевого продукта.

Нельзя строить UX по принципу:

- заказчик заполняет длинную форму;
- заказчик указывает договор, CI, бюджетные атрибуты, стратегические темы;
- заказчик фактически формирует спецификацию;
- AI только проверяет полноту формы;
- штаб подключается к общей форме и вручную разбирает, кто что должен заполнить.

Целевой принцип другой:

- заказчик сообщает потребность естественным языком;
- AI-агент помогает её уточнить и структурировать;
- штаб получает уже обработанную, объяснимую и проверяемую карточку;
- штаб принимает operational decisions;
- система генерирует артефакты и поддерживает процесс дальше.

## Описание продукта

### 1.1 Название и назначение

**AI-ассистируемое приложение для заказа IT-специалистов** — единое окно для привлечения внешних ИТ-специалистов в команды разработки банка.

Приложение помогает заказчикам быстро и естественно сформулировать потребность в ресурсах, помогает штабу обработать запрос без ручного сбора данных, связывает потребность с backlog, договорами, подрядчиками и бюджетом, и сопровождает процесс до фактического вывода специалистов.

### 1.2 Философия продукта

Система строится вокруг **трёх ключевых принципов**:

1. **Минимум ручного ввода** — AI обрабатывает максимум информации, пользователь вводит минимум
2. **Нет дублирования данных** — информация вводится один раз и переиспользуется во всех артефактах
3. **Сервис вместо бюрократии** — система избавляет заказчиков от лишних форм и бюджетных параметров

### 1.3 Проблемы, которые решает система

| Проблема | Решение |
|---|---|
| Заказчик заполняет большую форму с техническими параметрами | AI-агент автоматически собирает информацию через диалог |
| Информация дублируется в backlog, спецификации, расчётах | Single input / multiple reuse — данные вводятся один раз |
| Процесс блокируется из-за отсутствия информации, которая может быть уточнена позже | Критический путь без искусственных блокеров |
| Заказчик не знает, какой договор выбрать, какие роли доступны | AI и справочники подталкивают нужные данные заранее |
| Штаб собирает информацию с нуля при каждом новом запросе | Штаб получает предзаполненную карточку с анализом AI |
| Нет связи между потребностью и реальным backlog | Автоматическое или полуавтоматическое создание карточек Jira |


### 1.4 Что система должна заменить

Система должна заменить или существенно сократить:

- ручные переписки между заказчиком и штабом;
- пересылку неструктурированных описаний потребности;
- Excel-таблицы для сбора параметров спецификации;
- повторное внесение одних и тех же данных;
- ручную подготовку черновиков спецификаций;
- неформальные уточнения без логирования;
- непрозрачные статусы заявок;
- зависимость процесса от памяти конкретного сотрудника штаба.

### 1.5 Что система не должна делать

Система не должна:

- заставлять заказчика заполнять договорные и бюджетные параметры;
- требовать от заказчика знания номера договора;
- требовать от заказчика знания CI-кода;
- требовать от заказчика знания продуктового кода или стратегической темы;
- перекладывать на заказчика подготовку этапности спецификации;
- превращать AI в “проверяющего заполнение формы”;
- превращать workflow в collaborative Excel;
- блокировать вывод специалистов из-за вторичных параметров.

### 1.6 Основные пользователи

Основные пользователи:

- заказчики ресурсов;
- сотрудники штабов / бэк-офиса;
- администраторы системы;
- руководители, смотрящие метрики;
- сотрудники, отвечающие за договоры, бюджеты и контроль качества подрядчиков.

## Product Vision и целевая философия

### 2.1 Целевое состояние

Целевое состояние продукта — единая AI-assisted платформа для управления процессом привлечения внешних IT-специалистов.

Система должна обеспечивать:

- единое окно для заказчика;
- conversational intake;
- работу через текст, голос, файл, шаблон;
- структурирование потребности;
- нормализацию ролей и компетенций;
- сопоставление запроса с договорными ролями;
- помощь штабу в выборе договора и подрядчика;
- подготовку backlog-артефактов;
- подготовку draft спецификации;
- логирование и метрики end-to-end процесса;
- прозрачность статусов для заказчика и штаба.

### 2.2 Ключевой результат процесса

Ключевой результат — не документ и не заполненная форма.

Ключевой результат:

- потребность заказчика понята;
- запрос структурирован;
- штаб получил полную и проверяемую картину;
- подрядчик / договор выбран;
- downstream-артефакты подготовлены;
- специалисты фактически выведены или процесс их вывода прозрачно управляется.

### 2.3 Продуктовая философия

Система строится на принципах:

1. **Service over bureaucracy**  
   Заказчик не должен становиться оператором бэк-офиса.

2. **AI-first, not form-first**  
   Основной путь — диалог и естественный ввод, а не ручное заполнение сложной формы.

3. **Single input, multiple reuse**  
   Информация вводится один раз и дальше переиспользуется в заявке, backlog, спецификации, интеграциях и аналитике.

4. **Human-in-the-loop**  
   AI помогает, но не принимает финальные юридические, финансовые и договорные решения.

5. **Critical path, no artificial bottlenecks**  
   Процесс не должен блокироваться из-за информации, которую можно уточнить позже.

6. **Explainable automation**  
   Все выводы AI должны быть объяснимыми, проверяемыми и редактируемыми.

### 2.4 Позиционирование системы

Система **не является**:

- веб-формой;
- Excel replacement;
- генератором DOC/PDF;
- collaborative form filling tool;
- системой, перекладывающей работу штаба на заказчика.

Система **является**:

- AI-assisted staffing workflow platform;
- resource acquisition orchestration system;
- conversational intake platform;
- operational coordination layer;
- источником структурированных данных для downstream-процессов.


## Цели и задачи

### 2.1 Основные цели

1. **Сократить время сбора запроса** — с текущих часов/дней до минут
2. **Улучшить качество спецификаций** — структурированные данные, меньше ошибок
3. **Разгрузить штаб** — перенести рутину на AI-агента
4. **Улучшить UX заказчика** — взаимодействие через естественный язык, без форм
5. **Стандартизировать процесс** — единое окно для всех типов запросов
6. **Связать системы** — Jira, договоры, бюджет, спецификации в одном месте

### 2.2 Задачи MVP (первая итерация)

- [ ] Сбор запроса через AI-агент (основной workflow)
- [ ] Альтернативный workflow через шаблоны
- [ ] Структурирование ролей и компетенций
- [ ] Интеграция с Jira / SberTrack
- [ ] Интерфейс для сотрудника штаба (просмотр, верификация, уточнение)
- [ ] Генерация draft спецификации
- [ ] Логирование процесса


### 2.3 Расширенная классификация целей

#### Business goals

1. Сократить time-to-resource.
2. Уменьшить ручную нагрузку на штаб.
3. Повысить качество входящих запросов.
4. Снизить количество итераций уточнений.
5. Повысить прозрачность процесса.
6. Улучшить управляемость внешних ресурсов.
7. Сформировать основу для дальнейшей автоматизации контрактного процесса.

#### UX goals

1. Заказчик должен иметь возможность описать потребность обычным языком.
2. Заказчик не должен заполнять внутренние бюрократические поля.
3. Пользовательский путь должен быть короче старого процесса.
4. Интерфейс должен поддерживать несколько способов ввода.
5. Система должна объяснять, что она поняла.
6. Заказчик должен подтверждать результат, а не собирать спецификацию руками.

#### Operational goals

1. Штаб получает предзаполненную карточку заявки.
2. Штаб видит исходный текст, выводы AI, риски и пробелы.
3. Штаб может уточнить данные через единый чат.
4. Все уточнения сохраняются в истории заявки.
5. Все изменения логируются.
6. Статусы заявки однозначны и отслеживаемы.

#### Technical goals

1. Создать расширяемую архитектуру.
2. Разделить LLM-логику и deterministic business logic.
3. Обеспечить integration-first подход.
4. Поддержать graceful degradation.
5. Обеспечить auditability и traceability.
6. Сформировать основу для будущего target state.

## MVP Scope vs Target State

### 4.1 Принцип разделения

Документ описывает как целевое видение, так и MVP. Чтобы команда разработки не смешала эти уровни, все требования должны классифицироваться как:

- **Demo Prototype**;
- **MVP Core**;
- **MVP Optional**;
- **Target State**;
- **Out of Scope**.

### 4.2 Demo Prototype

Цель demo prototype — показать stakeholder’ам и разработчикам желаемый UX и workflow.

Demo prototype должен быть пригоден для размещения на Vercel.

Demo prototype может использовать:

- mocked backend;
- fake AI responses;
- локальные JSON-данные;
- имитацию интеграций;
- предзаготовленные сценарии.

Demo prototype не обязан иметь:

- реальную авторизацию;
- реальные интеграции;
- реальный GigaChat;
- production-grade backend;
- enterprise security.

### 4.3 MVP Core

В MVP Core входит:

- conversational intake;
- текстовый ввод;
- базовый шаблонный ввод;
- структурирование запроса;
- уточняющие вопросы;
- экран подтверждения запроса;
- уникальный номер заявки;
- кабинет “Мои заявки”;
- staff review workspace;
- чат заказчик ↔ штаб;
- базовое логирование;
- базовая data model;
- mock или ограниченная интеграция со справочником ролей;
- генерация простого draft спецификации;
- экспорт структурированного JSON.

### 4.4 MVP Optional

В MVP Optional входит:

- голосовой ввод;
- file upload;
- Jira read integration;
- Jira create integration;
- базовый contractor suggestion;
- версия draft specification в DOCX/PDF;
- дополнительные шаблоны подразделений;
- базовые SLA-метрики.

### 4.5 Target State

Target State включает:

- полноценную интеграцию с SberTrack;
- полноценную интеграцию с ЛК;
- интеграцию с МИП;
- contractor recommendation engine;
- прогнозирование сроков вывода;
- advanced analytics;
- автоматизированную подготовку конфигурационных файлов;
- интеграцию с контрактной системой;
- versioning спецификаций;
- lifecycle продления и изменений;
- расширенную ролевую модель;
- контроль качества подрядчиков.

## Target Operating Model

### 5.1 Заказчик

Заказчик — источник потребности и бизнес-контекста.

Заказчик должен:

- описать, какие специалисты нужны;
- объяснить, зачем они нужны;
- указать сроки и приоритеты;
- подтвердить структурированный запрос;
- отвечать на содержательные уточнения;
- согласовывать содержательную часть результата.

Заказчик не должен:

- выбирать договор;
- заполнять ставки;
- считать человеко-дни;
- знать CI;
- знать бюджетный контур;
- знать код продукта;
- формировать этапность спецификации.

### 5.2 AI-агент

AI-агент — активный участник процесса.

AI-агент должен:

- принять неструктурированный запрос;
- понять роли;
- понять уровни;
- понять сроки;
- понять требования;
- выявить пробелы;
- задать вопросы;
- нормализовать данные;
- сопоставить с ролями и справочниками;
- подготовить structured request;
- подготовить выводы для штаба;
- подготовить артефакты.

AI-агент не должен:

- принимать финальные решения;
- скрывать неопределённость;
- выдавать предположения как факты;
- выбирать подрядчика без человека;
- утверждать бюджет;
- создавать юридически значимые документы без подтверждения.

### 5.3 Штаб

Штаб — сервисный и операционный слой.

Штаб должен:

- получать enriched request;
- проверять выводы AI;
- выбирать договор и подрядчика;
- уточнять спорные вопросы;
- готовить или верифицировать спецификацию;
- согласовывать результат;
- запускать дальнейший процесс.

Штаб не должен:

- заново собирать базовые данные;
- вручную переносить данные между системами;
- работать с неструктурированным “мусором” без AI-предобработки.


## Архитектура системы

```
┌─────────────────────────────────────────────────────────────┐
│                    ФРОНТЕНД (React / HTML)                  │
├─────────────────────────────────────────────────────────────┤
│  Интерфейс заказчика  │  Интерфейс штаба  │  Admin console │
└────────────┬──────────────────────────┬──────────────────────┘
             │                          │
        ┌────▼──────────────────────────▼────┐
        │      BACKEND API (Node/Python)      │
        │  - REST endpoints                   │
        │  - Обработка бизнес-логики         │
        │  - Оркестрация интеграций          │
        └────┬──────────────────────┬─────────┘
             │                      │
    ┌────────┼──────────────────────┼────────┐
    │        │                      │        │
┌───▼──┐ ┌──▼────┐  ┌──────┐  ┌───▼───┐ ┌─▼──────┐
│GigaChat│ │Jira  │  │SberT │  │ЛК    │ │МИП    │
│ API  │ │ REST  │  │ API  │  │ API  │ │ API  │
└──────┘ └───────┘  └──────┘  └──────┘ └──────┘
    │        │         │         │        │
└────────────┴─────────┴─────────┴────────┘
      Внешние системы / Интеграции
```

### 3.2 Основные компоненты

**Backend-слой:**
- API Gateway — маршрутизация запросов
- Request Service — управление заявками (CRUD, статусы)
- AI Orchestrator — оркестрация вызовов Giga-chat
- Integration Layer — интеграции с Jira, справочниками, МИП
- Specification Generator — генерация draft спецификаций
- Notification Service — уведомления пользователям

**Frontend-слой:**
- Customer Interface — интерфейс заказчика (сбор запроса, мои заявки)
- Staff Interface — интерфейс штаба (карточка, верификация, спецификация)
- Admin Console — управление шаблонами, справочниками

**Data-слой:**
- Request Store — хранение заявок и истории
- Session Store — сессии диалогов с AI
- Template Store — шаблоны заявок
- Cache Layer — кэш справочников


### 3.3 Расширенная архитектурная логика v2.0

Исходная архитектура сохраняется, но для реализации enterprise-grade workflow необходимо явно выделить:

- Workflow Engine;
- AI Orchestrator;
- Integration Layer;
- Audit Service;
- Notification Service;
- Reference Data Service;
- Artifact Generation Service.

### 3.4 Deterministic vs AI logic

Система должна разделять LLM-логику и deterministic business logic.

LLM используется для:

- понимания естественного языка;
- извлечения ролей, сроков, требований;
- генерации уточняющих вопросов;
- summarization;
- подготовки draft-текстов.

Deterministic logic используется для:

- статусов заявки;
- правил переходов;
- RBAC;
- SLA;
- расчётов;
- сопоставления по справочникам;
- интеграций;
- audit trail;
- запрета недопустимых действий.

### 3.5 Event-driven mindset

Ключевые действия должны фиксироваться как события:

- request_created;
- raw_input_received;
- ai_analysis_started;
- ai_analysis_completed;
- clarification_required;
- structured_request_confirmed;
- submitted_to_staff;
- staff_review_started;
- contractor_selected;
- specification_generated;
- approval_requested;
- request_completed.

### 3.6 Integration-first design

Все интеграции должны проектироваться через adapter layer.

Это позволит:

- заменить Jira на SberTrack;
- использовать mock-интеграции в demo;
- не блокировать разработку UI;
- изолировать внешние API;
- обеспечить graceful degradation.

Обозначения:

### 4.4 Human-in-the-loop модель

Все критичные решения принимает человек.

AI:

- рекомендует;
- предлагает;
- ускоряет;
- автоматизирует рутину.

AI не должен:

- автоматически выбирать подрядчика;
- автоматически утверждать бюджет;
- автоматически подписывать спецификации;
- самостоятельно запускать юридически значимые действия.

### 4.5 Что заказчик не должен делать

Заказчик не должен:

- вводить номер договора;
- выбирать технический договорный справочник;
- указывать ставки;
- считать человеко-дни;

- выбирать бюджетный контур;
- заполнять стратегическую тему;
- формировать этапы спецификации;
- вручную переносить backlog в спецификацию;
- отвечать на вопросы, которые система может закрыть через справочники.

### 9.2 Описание статусов

#### Draft

Заявка создана, но потребность ещё не сформулирована.

Owner: заказчик.

Allowed actions:

- продолжить ввод;
- выбрать шаблон;
- загрузить файл;
- удалить черновик.

#### AI Intake

AI принимает первичное описание потребности.

Owner: AI.

Allowed actions:

- анализировать ввод;
- извлечь роли;
- извлечь сроки;
- извлечь требования;
- сформировать вопросы.

#### Awaiting Customer Clarification

AI обнаружил пробелы и ждёт уточнений.

Owner: заказчик.

Allowed actions:

- ответить на вопросы;
- изменить исходное описание;
- приложить файл;
- перейти к черновику с неполными данными.

#### Awaiting Customer Confirmation

AI сформировал structured request draft.

Owner: заказчик.

Allowed actions:

- подтвердить;
- отредактировать;
- задать вопрос;
- вернуть в AI Intake.

#### Submitted to Staff

Заявка передана штабу.

Owner: система / очередь штаба.

Allowed actions:

- назначить ответственного;
- взять в работу;
- вернуть на уточнение.

#### Staff Review

Штаб проверяет выводы AI.

Owner: сотрудник штаба.

Allowed actions:

- подтвердить данные;
- изменить данные;
- запросить уточнение;
- выбрать договор;
- отклонить как некорректную.

#### Contractor Selection

Штаб выбирает договор и подрядчика.

Owner: сотрудник штаба.

Allowed actions:

- выбрать вариант;
- запросить альтернативы;
- разделить команду по подрядчикам;
- уточнить у заказчика предпочтения.

#### Specification Drafting

AI и штаб готовят draft спецификации.

Owner: штаб.

Allowed actions:

- сгенерировать draft;
- отредактировать;
- сформировать конфигурационный файл;
- отправить на согласование.

#### Customer Approval

Заказчик согласует содержательную часть.

Owner: заказчик.

Allowed actions:

- согласовать;
- оставить комментарий;
- вернуть на доработку.

#### Contracting

Штаб запускает контрактный процесс.

Owner: штаб.

Allowed actions:

- передать в ЛК;
- сформировать пакет документов;
- зафиксировать external status.

#### Specialists Sourcing

Подрядчик / штаб ищет специалистов.

Owner: штаб.

Allowed actions:

- обновить статус;
- зафиксировать кандидатов;
- запросить изменение состава.

#### Specialists Onboarding

Специалисты выводятся в команду.

Owner: штаб / заказчик.

Allowed actions:

- подтвердить выход;
- зафиксировать дату;
- закрыть заявку.

#### Completed

Потребность закрыта.

Owner: система.

Allowed actions:

- посмотреть историю;
- создать повторную заявку;
- сохранить как шаблон;
- инициировать продление.


## Workflows и User Stories


### 5.0 End-to-end process overview

```text
Потребность заказчика
↓
AI intake
↓
Уточнение
↓
Структурированный запрос
↓
Подтверждение заказчиком
↓
Передача в штаб
↓
Проверка и enrich
↓
Выбор договора / подрядчика
↓
Backlog / Specification artifacts
↓
Согласование
↓
Вывод специалистов
↓
Завершение / изменение / продление
```

### 5.0.1 Critical path principle

Workflow должен отделять информацию, без которой процесс не может двигаться дальше, от информации, которую можно дозапросить позже.

Blocking information:

- кто заказчик;
- какие роли нужны;
- сколько специалистов;
- ориентировочные сроки;
- общий контекст потребности.

Non-blocking information:

- точный CI;
- точный договор;
- точный подрядчик;
- этапность спецификации;
- ставки;
- бюджетный контур;
- часть справочных атрибутов.

Non-blocking information не должна останавливать старт обработки заявки.

### 5.0.2 Workflow изменения заявки

Система должна поддерживать изменение заявки после первичного создания.

Изменения могут касаться:

- состава команды;
- количества специалистов;
- сроков;
- требований;
- подрядчика;
- backlog;
- этапности;
- продления.

При изменении должна создаваться версия или Change Request.


### 5.1 Основной workflow: Сбор запроса через AI-агента

**Участники:** Заказчик, AI-агент  
**Триггер:** Заказчик заходит в систему и нажимает "Создать новую заявку" или "Создать запрос"  
**Целевой результат:** Структурированная заявка, готовая к обработке штабом  

#### US-1.1: Заказчик начинает диалог с AI-агентом

```gherkin
Дано: Заказчик авторизован в системе
Когда: Заказчик нажимает "Новый запрос"
То: Система показывает экран взаимодействия с AI-агентом с приветствием и предложением описать потребность

Приветствие примерно:
"Привет! Я помогу вам подобрать специалистов.
Расскажите:
- Сколько людей и какие роли вам нужны
- На какой срок
- С какими требованиями

Вы можете:
📝 Написать текст
🎤 Рассказать голосом
📎 Загрузить файл или скопировать из другого источника"

Система поддерживает:
- Text input (обычный ввод)
- Voice input (голос → STT → обработка)
- File upload (TXT, MD, DOCX, PDF)
- Copy-paste
```

#### US-1.2: Заказчик описывает потребность

```gherkin
Дано: AI-агент готов к приёму входных данных
Когда: Заказчик описывает потребность (голосом, текстом или файлом)
То: Система распознает запрос и начинает уточняющий диалог

Примеры входных данных:
- "Мне нужна команда из 10 человек на 8 месяцев: 3 Java backend-разработчика (2 middle, 1 senior), 2 системных аналитика, 1 frontend-разработчик, 1 DevOps, 2 autotest QA. Нужен опыт с банковскими системами."
- [Загружен файл requirements.docx с подробным описанием]
- "Нам нужна поддержка текущей системы: 1 Java-разработчик, 1 QA, может быть DevOps на неполный день"
```

#### US-1.3: AI-агент задает уточняющие вопросы

```gherkin
Дано: AI распознал потребность
Когда: Система анализирует полноту информации
То: AI задает вопросы по существу (максимум 3-5 вопросов на этапе)

AI должен уточнить:
1. РОЛИ И УРОВНИ (если не ясно):
   - "Вы упомянули 'Java-разработчик'. Это backend-разработчик? На какой уровень: junior, middle, senior?"
   - "Сколько middle и сколько senior среди Java-разработчиков?"

2. СРОКИ (если не полные):
   - "Когда нужны аналитики?" → "Как можно раньше"
   - "А DevOps?" → "На неделю позже"
   - Система предлагает календаризацию

3. ТРЕБОВАНИЯ (если недостаточно):
   - "Какие технологии обязательны для Java-разработчиков?"
   - "Нужен опыт с Kafka, Spring, PostgreSQL?"
   - "Какие еще кастомные требования к команде?"

4. BACKLOG И КОНТЕКСТ (если нужно):
   - "Есть ли уже backlog в Jira / SberTrack?"
   - "Можете ссылку поделиться? Или опишу я на основании ваших слов?"

5. СРОКИ И ПРИОРИТЕТЫ (если критично):
   - "Это срочный запрос? На сколько дней вперед нужно все готово?"

Принцип: задавать только существенные вопросы, минимизировать беспокойство пользователя.
```

#### US-1.4: AI структурирует запрос и показывает черновик

```gherkin
Дано: AI собрал достаточно информации
Когда: AI формирует структурированный запрос
То: Система показывает заказчику черновик на подтверждение

Показывается примерно так:

════════════════════════════════════
📋 ВАШ ЗАПРОС (черновик)
════════════════════════════════════

👥 СОСТАВ КОМАНДЫ
├─ Java backend-разработчик (middle) × 2
├─ Java backend-разработчик (senior) × 1
├─ Системный аналитик × 2
├─ Frontend-разработчик (senior) × 1
├─ DevOps-инженер (senior) × 1
└─ Autotest QA (middle) × 2
   Total: 10 человек

⏱️ СРОКИ
├─ Начало: как можно раньше (целевая дата __)
├─ Окончание: через 8 месяцев
├─ Аналитики и backend: срочно
├─ Frontend и DevOps: в течение 2 недель
└─ QA: через месяц

🔧 ТРЕБОВАНИЯ ПО КОМПЕТЕНЦИЯМ
├─ Для Java backend: Spring, Kafka, PostgreSQL, REST API
├─ Для аналитиков: BPMN, системный анализ интеграций
├─ Для QA: Java, Selenium, API testing
└─ Для всей команды: опыт банковских систем

❓ УТОЧНЕНИЯ, КОТОРЫЕ МЫ СОБРАЛИ
├─ Это новый проект? [Ответ: нет, поддержка]
├─ Есть ли уже backlog? [Ответ: да, ссылка на Jira]
└─ Команда должна быть в одном месте? [Ответ: да, один подрядчик предпочтительно]

════════════════════════════════════
[✏️ Изменить] [✅ Подтвердить] [❓ Задать еще вопросы]
════════════════════════════════════

Заказчик может:
- Нажать ✅ Подтвердить — и идти дальше
- Нажать ✏️ Изменить — и отредактировать конкретный блок
- Нажать ❓ Задать еще вопросы — и углубиться в диалог
```

#### US-1.5: Заказчик подтверждает структурированный запрос

```gherkin
Дано: Показан черновик структурированного запроса
Когда: Заказчик нажимает ✅ Подтвердить
То: 
  1. Система создает заявку с уникальным номером (напр., REQ-2026-00521)
  2. Заявка переходит в статус "В обработке у штаба"
  3. AI формирует фоновые артефакты (см. US-1.6 и далее)
  4. Заказчику показывается статус и ссылка на "Мои заявки"
  5. Штабу приходит уведомление о новой заявке
```

#### US-1.6: AI генерирует черновики связанных артефактов (фоновый процесс)

```gherkin
Дано: Заявка создана
Когда: AI обрабатывает структурированный запрос
То: AI генерирует и готовит:

1. DRAFT BACKLOG В JIRA / SBERTRACK
   - AI анализирует описание потребности
   - Если backlog уже указан: подтягивает ссылки на Story
   - Если backlog не указан: генерирует черновой Epic/Story структуру
   - Создает карточки (или готовит для подтверждения):
     * Epic: "Поддержка системы Z на 8 месяцев"
       - Story 1: "Backend: реализовать интеграцию с X" (Sprint 1-2)
       - Story 2: "QA: покрытие тестами нового API" (Sprint 3+)
       - etc.

2. DRAFT ПРЕДМЕТА СПЕЦИФИКАЦИИ
   - На основании: запроса, backlog, договорных ролей
   - Примерно:
     "Привлечение команды из 10 специалистов на разработку и поддержку 
      системы Z сроком на 8 месяцев, включая:
      - backend-разработку (Java, Spring, Kafka)
      - системный анализ интеграционных взаимодействий
      - frontend-разработку (React)
      - DevOps поддержку (K8s, CI/CD)
      - автоматическое тестирование (Java, Selenium)
      в соответствии с договором [Номер договора] от [Дата]."

3. СПРАВОЧНЫЕ ДАННЫЕ
   - AI предлагает возможные сопоставления:
     * Продукт: [возможные варианты из каталога]
     * Стратегическая тема: [варианты]
     * Бюджетный контур: [варианты]
     * CI-коды: [варианты]

4. ВОЗМОЖНЫЕ ДОГОВОРЫ И ПОДРЯДЧИКИ
   - AI анализирует доступные договоры
   - Предлагает варианты закрытия потребности:
     * Вариант 1: Подрядчик A (все роли, срок вывода 2 недели)
     * Вариант 2: Подрядчик B (все роли, срок вывода 3 недели)
```

## UX Principles

### 11.1 Conversational-first

Основной пользовательский путь — диалог с AI.

Формы используются:

- для подтверждения;
- для редактирования;
- для staff review;
- для admin functions.

### 11.2 Progressive disclosure

Система не показывает все поля сразу.

Пользователь видит только:

- актуальный следующий шаг;
- понятные вопросы;
- результат интерпретации;
- действия, которые действительно нужны.

### 11.3 Flexible input

Система поддерживает:

- текст;
- голос;
- copy-paste;
- markdown;
- docx/pdf/txt upload;
- шаблоны;
- повтор заявки.

### 11.4 Customer is not back-office

UX должен исключать ситуации, когда заказчик:

- ищет договор;
- вводит CI;
- считает ставки;
- выбирает бюджетные атрибуты;
- заполняет спецификацию.

### 11.5 Staff workspace is not customer form

Интерфейс штаба должен быть отдельным рабочим пространством, а не тем же экраном, что у заказчика.

Штаб должен видеть:

- больше данных;
- справочную информацию;
- риски;
- системные подсказки;
- действия по процессу.

### 11.6 AI must explain

AI должен объяснять:

- что он понял;
- что не понял;
- где есть риск ошибки;
- какие данные взяты из справочника;
- какие данные являются предположением.

### 11.7 Role-based AI transparency

Прозрачность AI должна зависеть от роли пользователя.

Заказчик видит только business-readable summary:

- что система поняла из его запроса;
- какой состав команды сформирован;
- какие сроки и требования зафиксированы;
- какие содержательные вопросы нужно подтвердить или уточнить;
- что будет передано штабу дальше по процессу.

Заказчик не должен видеть техническую “кухню” AI-интерпретации:

- confidence score;
- source fragments;
- internal reasoning summary;
- reference matches;
- CI / product / budget inference;
- contractor assumptions;
- технические детали сопоставления со справочниками.

Сотрудник штаба видит verification layer:

- исходный ввод заказчика;
- извлечённые роли и требования;
- confidence по каждому выводу;
- source fragments;
- найденные противоречия;
- неопределённости;
- справочные совпадения;
- предположения AI;
- recommended next actions.

Администратор видит audit / debug layer:

- логи;
- ошибки интеграций;
- технические статусы обработки;
- audit trail;
- служебные данные, необходимые для поддержки и расследования инцидентов.

## Интеграции


### 7.0 Integration modes

Каждая интеграция должна иметь режим:

- **mock** — для demo prototype;
- **read-only** — для безопасного MVP;
- **write-enabled** — для production;
- **target production** — для финального целевого состояния.

### 7.0.1 Source of truth principle

AI не является source of truth для договоров, ставок, CI, продуктовых кодов или бюджетов.

Source of truth:

- договоры — contract catalog / договорная система;
- ставки — договорная система / справочник ставок;
- роли — role catalog;
- CI — CI catalog;
- backlog — Jira/SberTrack;
- статусы заявки — Request Service;
- действия пользователей — EventLog.

### 7.0.2 Fallback integration principle

Если внешняя интеграция недоступна:

- workflow не должен полностью останавливаться;
- создаётся pending integration task;
- пользователю показывается degraded mode;
- данные сохраняются локально;
- повторная синхронизация выполняется позже.


### 7.1 GigaChat API интеграция

#### Что интегрируется:

1. **Входящие данные:**
   - Текст (чат, запрос)
   - Голос (STT — Speech-to-Text)
   - Файлы (TXT, MD, DOCX, PDF с распознаванием текста)

2. **Исходящие операции:**
   - Отправка запроса на анализ
   - Получение структурированного ответа
   - Генерация уточняющих вопросов
   - Генерация черновиков (backlog, спецификация)
   - Проверка противоречий в требованиях

#### Пример API контракта:

```json

    "previousResponses": [...],
```

### 7.2 Jira REST API интеграция

#### Что интегрируется:

1. **Чтение:**
   - Получение Epic / Story по URL
   - Получение статуса задач
   - Чтение описания и требований

2. **Создание:**
   - Автоматическое создание Epic с драфт-требованиями
   - Создание Story для этапов разработки
   - Приложение ссылок на спецификацию

3. **Обновление:**
   - Обновление ссылок при уточнении требований
   - Обновление статусов при переходе заявки между этапами

#### Пример API контракта:

```json
// Запрос на создание Epic
POST /jira/api/3/issues
{
  "fields": {
    "project": {"key": "SYZ"},
    "issuetype": {"name": "Epic"},
    "summary": "Привлечение команды для поддержки Системы Z",
    "description": "...",
    "customfield_epic_name": "Система Z - 8 месяцев",
    "labels": ["recruiting", "external-team", "system-z"],
    "components": [{"name": "Backend"}]
  }
}

// Ответ
{
  "id": "10000",
  "key": "SYZ-123",
  "self": "https://jira.bank/rest/api/3/issue/10000"
}
```

### 7.3 SberTrack интеграция

Аналогична Jira. Основные различия:
- API endpoint может отличаться
- Поля и типы задач могут быть другими
- Нужна адаптация логики создания карточек

### 7.4 Интеграция со справочниками

#### Справочники (Reference Data):

1. **Справочник ролей** (Role Catalog)
   ```json
   {
     "roles": [
       {"id": "java_backend", "name": "Java backend-разработчик", 
        "levels": ["junior", "middle", "senior"],
        "defaultTariff": 95},
       {"id": "frontend_dev", "name": "Frontend-разработчик", ...}
     ]
   }
   ```

2. **Справочник договоров** (Contract Catalog)
   ```json
   {
     "contracts": [
       {"id": "45-2024", "contractor": "Tech Solutions LLC",
        "availableRoles": ["java_backend", "frontend_dev", ...],
        "tariffs": {"java_backend": {"middle": 95, "senior": 130}},
        "budgetRemaining": 850000}
     ]
   }
   ```

3. **Справочник продуктов** (Product Catalog)
   ```json
   {
     "products": [
       {"code": "SYS-Z", "name": "Система Z", "owner": "..."}
     ]
   }
   ```

4. **Справочник систем и CI-кодов** (CI Catalog)
   ```json
   {
     "systems": [
       {"ci": "SYS-Z-001", "name": "Система Z", "team": "Backend"}
     ]
   }
   ```

   ```
       "team": [...],

       "requirements": [...],
       "budget": {...}
     }
   }
   ```

## Требования к AI-агенту (Giga-chat)

### 8.1 Основные возможности

#### 1. Распознавание потребности в ресурсах

**Что должен уметь:**
- Разбирать текст, голос, файлы
- Извлекать:
  - Роли и должности (java backend, frontend, QA, etc.)
  - Уровни компетенций (junior, middle, senior)
  - Количество специалистов
  - Сроки и даты старта
  - Требования к компетенциям и технологиям

**Пример:**
```
Вход: "Мне нужна команда из 10 человек на 8 месяцев: 
       3 Java backend (2 middle, 1 senior), 
       2 аналитика, 1 frontend senior, 1 DevOps, 2 QA..."

Выход:
{
  "roles": [
    {"title": "Java backend", "level": "middle", "count": 2},
    {"title": "Java backend", "level": "senior", "count": 1},
    ...
  ],
  "duration": "8 months",
  "startDate": "ASAP",
  "confidence": 0.95
}
```

#### 2. Задавание уточняющих вопросов

**Логика:**
- Выявить пробелы в информации
- Задать максимум 3-5 вопросов за раз
- Вопросы должны быть по существу, не бюрократические
- Не спрашивать информацию, которая может быть в справочниках

**Примеры вопросов, которые нужно задать:**
- "Какая точная дата старта?" (если указано "ASAP")
- "Какие технологии обязательны?" (если не указаны)
- "Есть ли уже backlog в Jira?" (важно для процесса)

**Примеры вопросов, которые НЕ нужно задавать:**
- "Какой номер договора?" (выберет штаб)
- "Какой продукт?" (может быть уточнено позже)
- "Какие бюджетные коды?" (не зона заказчика)

#### 3. Проверка противоречий и полноты

**Что проверять:**
- Junior developer с опытом 10 лет → противоречие
- Backend-роль с frontend-стеком → ошибка
- Senior без ключевых технологий → неполнота
- Требование "недели вывода" при сложной роли → нереалистично
- Одна компетенция названа разными словами → нормализовать

**Как реагировать:**
- Не блокировать процесс, а подсветить и спросить
- "Вы указали junior + 10 лет опыта. Возможно, это senior?"

#### 4. Структурирование и нормализация

**Что нормализировать:**
- Варианты названий ролей:
  - "Java-разработчик backend" → "Java backend-разработчик"
  - "QA автотесты" → "Autotest QA"
- Варианты технологий:
  - "Spring boot" → "Spring Framework"
  - "PG" → "PostgreSQL"
- Сроки:
  - "Скорее всего в июне" → уточнить дату
  - "Максимум 3 месяца" → дата окончания

#### 5. Подтягивание справочных данных

**Что подтягивать:**
- **Договорные роли:** сопоставить запрос с доступными ролями в договорах
- **Тарифы:** показать ожидаемую стоимость
- **Подрядчики:** предложить вариант закрытия потребности
- **CI-коды:** предложить коды автоматизированных систем
- **Продукты:** предложить соответствующие продукты каталога

#### 6. Генерация черновиков артефактов

**Что генерировать:**

1. **Draft Backlog / Epic-Story структура**
   - На основе потребности и backlog из Jira
   - Story должны быть конкретные и оценимые

2. **Draft Предмета спецификации**
   - Формальный текст, готовый к редактированию штабом
   - На основе: запроса, договора, ролей, компетенций

3. **Draft Требований по компетенциям**
   - Для каждой роли отдельно
   - Разделение на обязательные и желательные

4. **Draft Этапности**
   - На основе backlog и сроков
   - Примерное распределение ролей по этапам

### 8.2 Интеграционные требования

#### Входные источники данных:

```
GigaChat должен иметь доступ к:
├─ Текстовый ввод заказчика (API backend)
├─ Голосовые данные (STT обработка)
├─ Загруженные файлы (TXT, MD, DOCX, PDF)
├─ История диалога (session store)
├─ Справочники (API к МИП и локальным справочникам)
└─ Jira / SberTrack (для поиска существующего backlog)
```

#### Выходные действия:

```
GigaChat должен сгенерировать:
├─ Структурированный JSON с анализом
├─ Уточняющие вопросы (список)
├─ Сопоставления с договорными ролями
├─ Предложения подрядчиков
├─ Черновики спецификаций
└─ Логирование всех шагов для аудита
```


### 8.3 AI Governance

#### 8.3.1 Human-in-the-loop

AI не принимает финальных решений.

AI может:

- предложить;
- структурировать;
- объяснить;
- подсветить риск;
- сформировать draft.

Человек должен подтверждать:

- выбор подрядчика;
- выбор договора;
- бюджетную корректность;
- запуск downstream-процесса;
- финальную версию спецификации;
- юридически значимые действия.

#### 8.3.2 Fact vs Assumption

AI должен явно разделять:

- факты из исходного запроса;
- данные из справочников;
- предположения;
- рекомендации;
- неопределённости.

#### 8.3.3 Confidence Score

Каждый AI-вывод должен иметь confidence score.

Пример:

```json
{
  "field": "product",
  "value": "Система Z",
  "confidence": 0.84,
  "source": "inferred from user input and CI catalog",
  "requiresHumanConfirmation": true
}
```

#### 8.3.4 Anti-hallucination rules

AI обязан:

- не выдумывать договоры;
- не выдумывать ставки;
- не выдумывать CI;
- не выдумывать бюджет;
- не выдавать предположения как факт;
- показывать “не найдено”, если данных нет;
- показывать варианты, если их несколько;
- передавать low-confidence результаты на проверку штабу.

## Non-Functional Requirements

### 10.1 Performance

- **Время отклика API:** < 200ms для запросов к справочникам
- **Время анализа AI:** до 10 секунд для текстового запроса
- **Время загрузки интерфейса:** < 2s (Largest Contentful Paint)
- **Поддержка одновременных пользователей:** 500+ (MVP), 5000+ (production)

### 10.2 Reliability

- **Uptime:** 99.5%
- **Сохранение состояния сессии:** если соединение разорвалось, заказчик может вернуться и продолжить
- **Резервное копирование:** все заявки и сессии бэкапятся ежедневно
- **Recovery Time Objective (RTO):** < 1 час

### 10.3 Scalability

- Горизонтальное масштабирование backend-сервисов
- Кэширование справочников (Redis)
- Использование асинхронных очередей для генерации спецификаций

### 10.4 Security

- **Аутентификация:** LDAP / SSO (корпоративный банк SSO)
- **Авторизация:** RBAC (Role-Based Access Control)
  - Заказчик видит только свои заявки
  - Штаб видит заявки, назначенные на него или всю очередь
  - Админ видит всё и может настраивать справочники
- **Шифрование в transit:** TLS 1.3
- **Шифрование at rest:** AES-256 для конфиденциальных данных
- **Логирование действий:** все изменения и действия логируются для аудита

### 10.5 Usability

- **Доступность:** WCAG 2.1 AA (поддержка скринридеров, контрастность текста)
- **Мобильность:** responsive design для планшетов (iPad), основной интерфейс на десктоп
- **Многоязычность:** минимум русский язык, готовность к английскому

### 10.6 Data Privacy

- **GDPR compliance:** если есть EU пользователи (для банка это может быть не критично, но стоит предусмотреть)
- **Right to be forgotten:** заказчик может запросить удаление своих данных
- **Data minimization:** система собирает только необходимые данные


### 10.7 Graceful degradation

Если AI недоступен:

- пользователь может сохранить черновик;
- может перейти к шаблону;
- штаб может обработать заявку вручную;
- система показывает degraded mode.

Если Jira / SberTrack недоступны:

- backlink создаётся как pending;
- workflow может продолжаться;
- sync выполняется позже.

Если справочник недоступен:

- AI не должен выдумывать данные;
- система помечает reference match как unavailable;
- штаб получает задачу ручной проверки.

### 10.8 Auditability

Система должна хранить:

- кто изменил заявку;
- когда изменил;
- что изменил;
- почему изменил;
- какой AI inference использовался;
- кто подтвердил AI inference.

### 10.9 Observability

Нужны:

- logs;
- metrics;
- traces;
- AI latency;
- integration error rate;
- queue health;
- SLA breach alerts.

### 10.10 AI Safety

Система должна:

- ограничивать автономность AI;
- требовать human confirmation;
- логировать AI output;
- хранить reasoning summary;
- отслеживать hallucination incident;
- поддерживать manual override.

## Acceptance Criteria

### 24.1 Demo acceptance criteria

Demo считается успешным, если:

- пользователь может пройти end-to-end сценарий от потребности до draft спецификации;
- заказчик взаимодействует через AI-first UX;
- штаб видит отдельный workspace;
- workflow не выглядит как длинная форма;
- есть статусы заявки;
- есть mock AI analysis;
- есть mock contractor options;
- есть mock draft specification;
- прототип можно показать на Vercel.

### 24.2 MVP acceptance criteria

MVP считается успешным, если:

- заявка создаётся с уникальным номером;
- AI формирует structured request;
- заказчик подтверждает structured request;
- штаб получает карточку заявки;
- штаб может верифицировать данные;
- работает чат уточнений;
- создаётся draft спецификации;
- все ключевые события логируются;
- данные не вводятся повторно;
- заказчик не заполняет договорные поля.

## Риски и ограничения

### 25.1 Product risks

- Пользователи могут продолжить писать в чатах вне системы.
- Штаб может не доверять AI.
- Заказчики могут не захотеть отвечать на уточнения.
- Слишком сложный MVP может сорваться.

Mitigation:

- сделать простой demo;
- быстро проверить UX;
- ограничить MVP;
- показать выгоду штабу.

### 25.2 Technical risks

- GigaChat может ошибаться.
- Справочники могут быть неполными.
- Интеграции могут быть недоступны.
- Jira/SberTrack migration может изменить требования.

Mitigation:

- mock mode;
- confidence;
- human-in-the-loop;
- adapter-based integrations;
- graceful degradation.

### 25.3 Organizational risks

- Неочевидно, кто owner процесса.
- Подразделения могут иметь разные договорные контуры.
- Процесс может отличаться по трайбам.
- Часть коммуникации может остаться неформальной.

Mitigation:

- role model;
- configurable workflows;
- SLA;
- analytics;
- шаблоны подразделений.
