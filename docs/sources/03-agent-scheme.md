# 03. Схема работы агента внутри сервиса, все зависимости

## Слайд 1. Работа агента внутри сервиса — основной флоу, шаги 1–6

1. Заказчик начинает диалог в веб-сервисе (вход по СУДИР): описывает потребность, при необходимости прикладывает документы. *(Человек)*
2. Обработка входной информации: классификация, извлечение ролей и сроков, нормализация по справочникам. *(LLM)*
   - 2а. Вопрос по процессу оформления — ответ через AI (база знаний процесса). *(LLM)*
3. Проверка и валидация заявки (полнота данных, формат документов, сверка с договором). *(Алгоритм)*
   - Ромб «Есть ошибки / комментарии / уточнения?» — **да** → 3а; **нет** → 4.
   - 3а. AI-общение: список ошибок передаётся в модель, пояснения возвращаются пользователю. *(LLM)*
4. Формирует проект спецификации, готовый к отправке на согласование. *(LLM + Алгоритм)*
5. Решение за человеком (исполнитель штаба) — на первое время. *(Человек)*
   - Процесс согласования в разных системах — не участвует в разработке.
   - Этап выполнения работ — не участвует в разработке.
6. **Этап 2 — после реализации основного процесса:** проверка артефактов и подготовка запуска оплаты.

## Слайд 2. Карта зависимостей агента

**Внутренние компоненты StaffAI:** веб-интерфейс (заказчик и штаб); AI-оркестратор; механизм валидации; генератор артефактов; Backend API, статусы, аудит; БД: заявки, сессии, версии, события.

**Внешние зависимости Этапа 1:** СУДИР (единый вход); GigaChat (языковая модель); хранилище договоров (роли, тарифы, бюджет); справочники (роли, грейды, продукты, CI); ЛК заказчика ИТ-ресурсов (конфигурация → черновик ЗНР → ЭДО); СберТрек / Jira (пакет Epic и Story); ЕСУП (через ЛК).

**Этап 2 / перспектива:** библиотека знаний (Jira/Confluence); Пульс ЕК; ServiceManager; FinAI (инициативы); целевая АС: оплата, НМА (при миграции).

## Слайд 3. Пошаговая расшифровка и правила исполнения

| Шаг | Кто / что | Вход | Выход | Тип |
|---|---|---|---|---|
| 1 | Заказчик (веб-сервис, СУДИР) | Потребность (текст, файл, шаблон) | Исходный ввод, сессия диалога | Человек |
| 2 | AI-агент | Исходный ввод | Классификация; структурированный черновик (роли, грейды, кол-во, сроки, стек); уточняющие вопросы (не более 3–5) | LLM |
| 2а | AI-агент | Вопрос по процессу | Ответ из базы знаний процесса, без создания заявки | LLM |
| 3 | Валидатор | Черновик + приложенные документы | Отчёт о проверке (флаги: превышение, близко к лимиту, требуется продление) | Алгоритм |
| 3а | AI-агент | Список ошибок | Пояснения пользователю простым языком; цикл до устранения, лимит итераций и эскалация | LLM |
| 4 | Генератор артефактов | Подтверждённая карточка + договор и ставки + шаблон | Проект спецификации (DOCX/PDF и JSON), версия | LLM + Алгоритм |
| 5 | Исполнитель (штаб) | Проект спецификации и слой проверки | Решение: отправить / вернуть / скорректировать | Человек |
| 5а | Система | Решение «отправить» | Рассылка: подрядчик (почта), исполнитель, заказчик; статус «Отправлено на согласование» | Алгоритм |
| — | Согласование в разных системах и этап выполнения работ — существующие процессы, в разработку не входят | | | |
| 6 | Этап 2 | Артефакты выполнения | Проверка артефактов, подготовка запуска оплаты | Этап 2 |
| — | Оплата (контроль у штаба) и НМА — целевая АС при миграции, в периметр не входят | | | |

### Правила исполнения (сквозные)

- **Решение человека:** шаг 5 всегда за исполнителем «на первое время»; автоотправка — только после накопления метрик качества и отдельного решения.
- **Достоверность:** модель не выдумывает договоры, ставки, CI, бюджет; всё справочное — только из хранилища и справочников; «не найдено» вместо догадки; выводы с низкой уверенностью — на проверку штабу.
- **Устойчивость к сбоям:** недоступность внешних систем не останавливает конвейер — отложенная задача, ограниченный режим, повторная синхронизация; недоступность модели — сохранение черновика и ручная обработка.
- **Единый жизненный цикл:** каждый запрос образует одну сущность «Заявка» с общими статусами и историей событий (аудит).
- **Разделение слоёв:** статусы, доступ, валидация, рассылки — только алгоритм; интерпретация, диалог, генерация текста — модель.
