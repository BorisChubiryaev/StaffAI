# AI-агент: функции, правила, контракт

> Источник: ТЗ v3 §6.3 (ФТ-3.x, ПР-1…ПР-5); ts-v2 §8 (детализация, контракт); схема агента. Речь об агенте **внутри
> продукта** (на GigaChat). Правила для ИИ-ассистентов, которые пишут код, — в [AGENTS.md](../../AGENTS.md).

## Что делает агент (ФТ-3.x)

| # | Функция | Тип |
|---|---|---|
| ФТ-3.1 | Извлечение из текста и файлов: роли, грейды, количество, сроки и календаризация, стек, формат работы, контекст | LLM |
| ФТ-3.2 | Нормализация по справочникам с фиксацией сопоставлений и уверенности | Hybrid: LLM предлагает кандидатов, алгоритм проверяет по справочнику |
| ФТ-3.3 | Уточняющие вопросы: только содержательные, ≤3–5 за итерацию; не переспрашивать указанное; не спрашивать то, что закрывается справочниками | LLM |
| ФТ-3.4 | Выявление противоречий (грейд vs опыт, роль vs стек) — подсветка без блокировки | LLM (+ детерминированные правила, где возможно) |
| ФТ-3.5 | Обогащение данными договоров и справочников; формирование вариантов подрядчиков | Hybrid: данные и расчёты — алгоритм, обоснование — LLM |
| ФТ-3.6 | Генерация артефактов: карточка, пояснения ошибок, тексты проекта спецификации, пакеты для ЛК и трекера | Шаблон + LLM (структура и числа — алгоритм) |
| ФТ-3.7 | Ответы на вопросы о процессе по базе знаний (прил. В, наполняет штаб) | LLM + поиск по базе знаний |
| ФТ-3.8 | Структурированный выходной контракт (JSON) | — |

## Обязательные правила (ПР)

| # | Правило | Как проверяется |
|---|---|---|
| **ПР-1** | Разделять **факты** (ввод пользователя), **справочные данные** и **предположения** во всех выводах | Каждое значение в контракте имеет `origin: user \| reference \| assumption` |
| **ПР-2** | Уверенность для каждого вывода; низкая уверенность → на проверку исполнителю | `confidence` обязателен; порог — конфигурация (ОВ-08) |
| **ПР-3** | **Не генерировать** договоры, ставки, CI, бюджеты. Нет данных → «не найдено»; неоднозначно → варианты | Значения этих полей принимаются только из адаптеров КАП/справочников; eval-тесты на галлюцинации |
| **ПР-4** | Все AI-выводы журналируются и доступны для проверки (кто подтвердил, что исправлено) | `AiInference` + события `ai_inference_confirmed/corrected` |
| **ПР-5** | LLM **не используется** для статусных переходов, контроля доступа, расчётов, валидации по справочникам, рассылок | Архитектурно: модель не имеет инструментов на эти действия |

## Разделение ответственности LLM / алгоритм

| Функция | Кто |
|---|---|
| Понимание текста, извлечение ролей/сроков/требований | LLM |
| Уточняющие вопросы, пояснения ошибок, тексты спецификации, ответы по базе знаний | LLM |
| Нормализация ролей и технологий | Hybrid |
| Проверка по справочникам, проверка по договорам КАП | Алгоритм |
| Расчёты (стоимость, человеко-дни, остаток бюджета) | Алгоритм |
| Рекомендация подрядчика | Hybrid (скоринг — алгоритм, объяснение — LLM) |
| Статусы, RBAC, рассылки, уведомления, аудит | Алгоритм |
| Выбор подрядчика, отправка на согласование | **Человек** |

## Выходной контракт (ФТ-3.8) — рабочая версия

Финальная схема фиксируется в спецификации `010-llm-orchestration` (JSON Schema в `contracts/`). Основа — ts-v2 §8.4 + ПР-1.

```json
{
  "requestId": "…",
  "classification": "staffing_request | process_question | other",
  "recognized": {
    "roles": [
      {
        "role":   { "value": "Java backend-разработчик", "catalogId": "java_backend", "origin": "reference", "confidence": 0.91 },
        "grade":  { "value": "middle", "origin": "user", "confidence": 0.94 },
        "count":  { "value": 2, "origin": "user", "confidence": 0.97 },
        "start":  { "value": null, "origin": "user", "confidence": 0.0, "status": "not_found" },
        "requirements": { "required": ["Spring", "Kafka"], "desired": ["опыт банковских систем"] },
        "sourceFragment": "3 Java backend-разработчика (2 middle, 1 senior)"
      }
    ],
    "timeline": { "duration": "8 months", "startPreference": "ASAP", "calendarization": [] },
    "workFormat": null,
    "context": "Поддержка системы Z"
  },
  "assumptions": [ { "field": "…", "value": "…", "reason": "…" } ],
  "uncertainties": [ { "field": "frontend stack", "reason": "not provided", "recommendedQuestion": "Какие технологии нужны для frontend?" } ],
  "contradictions": [ { "fields": ["grade", "experience"], "description": "junior с опытом 10 лет", "suggestion": "senior?" } ],
  "questions": ["…"],
  "nextBestAction": "ask_clarification | customer_confirmation_required | answer_process_question | escalate_to_executor"
}
```

`nextBestAction` — **рекомендация**; переход статуса выполняет детерминированная логика.

## Качество и безопасность

- **Эталонный набор** реальных (обезличенных) запросов собирается со штабом (Ф2, задача 2.10); точность извлечения —
  gate Ф2. Eval-прогон — часть CI для любых изменений промптов.
- Промпты — артефакты кода: версионируются в репозитории, меняются через PR со сравнением eval до/после.
- Деградация: при недоступности GigaChat — сохранение черновика, шаблонный путь, ручная обработка штабом.
- Метрики: точность извлечения, число итераций уточнений, доля ручных корректировок, доля low-confidence, инциденты
  недостоверной генерации, latency.
- Реальные данные обрабатываются **только** GigaChat в контуре банка (ТУ-04, ТУ-10).
