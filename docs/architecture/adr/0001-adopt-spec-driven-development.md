# ADR-0001. Разработка через спецификации (SDD)

- **Статус:** Принято
- **Дата:** 2026-10-15
- **Контекст решения:** старт проекта StaffAI

## Контекст

Требования к StaffAI распределены по нескольким документам разных версий (ТЗ v3, ТЗ v2, Видение, Этапы, схемы, замечания)
и содержат открытые вопросы (АР-01…02, ТУ-01…11). Значительную часть кода планируется писать с помощью ИИ-ассистентов.
Без единой точки истины и явных спецификаций ИИ и люди будут по-разному интерпретировать требования, а расхождения
между версиями источников — попадать в код.

## Решение

1. Источник истины о продукте — `docs/` (синтез) поверх `docs/sources/` (первичка) с явной иерархией источников.
2. Нормативные принципы — `.specify/memory/constitution.md`; любой план проходит проверку на соответствие.
3. Любая фича реализуется по циклу: **Intent → spec.md → clarify → plan.md → tasks.md → implement → analyze**,
   артефакты — в `specs/NNN-name/`. Код без утверждённой спецификации не мержится (кроме исправлений и chores).
4. Требования трассируются: ФТ/ПР/ИВ/ПС ТЗ → спецификация → задачи → тесты (`docs/requirements/traceability.md`).
5. Структура совместима с GitHub Spec Kit (`.specify/`, `specs/NNN-*`), команды адаптированы под проект (`.claude/commands/sdd.*`).

## Последствия

- (+) Новые участники и ИИ-агенты получают контекст из одного места; меньше переделок.
- (+) Открытые вопросы видны и не превращаются в тихие допущения в коде.
- (−) Накладные расходы на написание спецификаций; смягчается шаблонами и командами.
- Требуется дисциплина: изменения требований идут через обновление спецификации, а не только кода.
