# ADR-0002. Детерминированное ядро, LLM на периферии; интеграции через адаптеры

- **Статус:** Принято (прямо следует из ТЗ v3: ПР-5, ФТ-6.4, §7.1)
- **Дата:** 2026-10-15

## Контекст

LLM (GigaChat) может ошибаться и недоступна со 100% надёжностью. Процесс содержит юридически и финансово значимые шаги.
Внешние системы (КАП, ЛК, трекер, справочники) имеют неподтверждённые API и сроки готовности.

## Решение

1. Статусные переходы, контроль доступа, расчёты, валидация по справочникам и договорам, рассылки и уведомления
   реализуются **только детерминированным кодом**. Модель не получает инструментов для этих действий.
2. LLM используется для: классификации обращения, извлечения и нормализации (с проверкой по справочнику кодом),
   уточняющих вопросов, выявления противоречий, пояснения ошибок, текстов артефактов, ответов по базе знаний.
3. Ответ LLM — строго по JSON-контракту (ФТ-3.8), валидируется схемой; невалидный ответ = ошибка вызова, не данные.
4. Каждая внешняя система — за адаптером с режимами `mock` / `read_only` / `read_write`, переключаемыми конфигурацией.
   Недоступность → отложенная задача синхронизации и деградированный режим, а не остановка процесса.

## Последствия

- (+) Предсказуемость и аудируемость ключевых решений; тестируемость ядра без LLM.
- (+) Разработка не блокируется неготовностью КАП/ЛК (режим `mock`).
- (−) Больше кода на стыке LLM ↔ алгоритм (валидация контракта, сопоставление со справочниками).
