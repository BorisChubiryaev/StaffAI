# StaffAI за 10 минут

Документ для нового участника команды (человека или ИИ-агента). Прочитайте целиком — дальше по ссылкам по мере надобности.

## 1. Что мы строим

**StaffAI** — внутренний веб-сервис банка с AI-агентом на GigaChat. Владелец продукта пишет в чат, кого ему нужно
(«3 Java-бэкендера, 2 middle и senior, на 8 месяцев, срочно»), агент уточняет детали, система проверяет запрос по договорам
и справочникам, формирует карточку запроса, а сотрудник штаба получает её уже разобранной, выбирает подрядчика и
отправляет сгенерированный проект спецификации на согласование. На выходе — пакет данных для ЗНР в ЛК и пакет задач
для трекера. **Без повторного ввода данных и без договорной бюрократии для заказчика.**

> Заказчик говорит — система делает — человек решает.

Подробно: [видение](product/vision.md).

## 2. Зачем

Сейчас заказ внешних специалистов — недели ручной переписки. Заказчик вынужден знать номера договоров, бюджетные коды,
CI и формат ЗНР. Одни и те же данные вводятся 3–4 раза. Штаб вручную собирает недостающее по каждой заявке.
Цель — от обращения до проверенного запроса за минуты–часы, полный цикл до ЗНР — в 2+ раза быстрее.

## 3. Кто участвует

| Роль | В двух словах |
|---|---|
| **Заказчик** | Описывает потребность, отвечает на вопросы, подтверждает карточку. Не видит договоров, ставок и «кухни» AI |
| **Исполнитель (штаб)** | Проверяет выводы AI, уточняет, выбирает подрядчика, правит и отправляет проект спецификации |
| **Администратор** | Шаблоны, справочники, доступы, журналы |
| **AI-агент** | Понимает, структурирует, спрашивает, объясняет, пишет черновики. **Ничего не решает** |
| Подрядчик | Вне системы, получает проект спецификации по почте |

## 4. Как устроен процесс

```text
Заказчик ─► диалог с агентом ─► уточнения ─► проверка (алгоритм + КАП) ─┬─► ошибки? ─► пояснения ─┐
                                                                         │                         │
            ◄────────────────────────────────────────────────────────────┴──────────◄──────────────┘
         ─► карточка ─► подтверждение ─► очередь штаба ─► верификация, выбор подрядчика
         ─► проект спецификации ─► РЕШЕНИЕ ИСПОЛНИТЕЛЯ ─► рассылка на согласование
         ─► пакет JSON для ЛК (ЗНР) + пакет для трекера ─► [дальше — действующие системы]
```

Схема с деталями: [процесс](domain/process.md) · статусы: [жизненный цикл заявки](domain/request-lifecycle.md).

## 5. Пять правил, которые нельзя нарушать

1. **Заказчик не вводит** договор, ставки, CI, бюджетные коды, этапы спецификации — ни в UI, ни в API.
2. **Решения — за человеком:** подрядчик, бюджет, отправка на согласование. AI только рекомендует.
3. **LLM не управляет системой:** статусы, доступ, расчёты, проверки, рассылки — детерминированный код.
4. **Модель не выдумывает** договоры, ставки, CI, бюджеты. Нет данных — «не найдено». У каждого вывода — уверенность и источник.
5. **Всё значимое — в журнал событий**, всё изменяемое — версионируется. Сбой внешней системы — деградация, а не остановка.

Полная нормативная версия — [конституция проекта](../.specify/memory/constitution.md).

## 6. Что в MVP, а что нет

**В MVP (Этап 1):** веб-диалог (текст, файлы, шаблоны) → уточнения → проверка и валидация с циклом пояснений → карточка →
рабочее место штаба → варианты подрядчиков → проект спецификации (версии, DOCX/PDF/JSON) → решение → рассылка →
конфигурационный пакет для ЛК и пакет для трекера. Ответы на вопросы по процессу по базе знаний.

**Не в MVP:** голос, почтовый канал, автосоздание Epic/Story, создание ЗНР через API, оплата, НМА, автономные решения AI.

Подробно: [границы MVP](product/scope-mvp.md) · сроки: [дорожная карта](product/roadmap.md) (5–6 мес до ПРОМ, фазы Ф0–Ф6).

## 8. Как начать работать

1. Запустите прототип и пройдите демо-сценарий (13 шагов, ~15 минут) — это самый быстрый способ почувствовать продукт.
   Помните: прототип — иллюстрация, местами он шире MVP ([расхождения](sources/README.md#известные-расхождения-между-источниками)).
2. Прочитайте [процесс SDD](sdd-process.md) — любая фича делается через спецификацию.
3. Возьмите спецификацию из [реестра](../specs/README.md#реестр-спецификаций) в своей фазе; если её нет — создайте `/sdd.specify`.
4. Нашли противоречие или пробел в требованиях — не додумывайте: `[NEEDS CLARIFICATION]` в спецификации + строка в
   [open-questions.md](open-questions.md).

Для ИИ-ассистентов точка входа — [AGENTS.md](../AGENTS.md) (Claude Code читает его через [CLAUDE.md](../CLAUDE.md)).
