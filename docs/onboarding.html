StaffAI

Владелец продукта описывает, каких ИТ-специалистов ему нужно, один раз и простым языком. StaffAI превращает это в проверенную заявку, проект спецификации и данные для ЗНР. Решения остаются за человеком.

Зачем

Заказ внешних специалистов занимает недели

Заказчику приходится знать номера договоров, бюджетные коды, CI и формат ЗНР, хотя это не его работа. Одни и те же данные вводятся несколько раз. Штаб получает сырые запросы и вручную собирает недостающее по каждой заявке.

Кто участвует

У каждого своя зона, и они не пересекаются

customer

Заказчик

  • описывает потребность: текст, файл, шаблон
  • отвечает на уточнения
  • подтверждает карточку запроса
  • не выбирает договор и подрядчика
  • не вводит ставки, CI, бюджет
staff

Исполнитель (штаб)

  • проверяет выводы AI
  • уточняет у заказчика в чате
  • выбирает подрядчика
  • правит и отправляет проект спецификации
  • не собирает данные с нуля
  • не переносит данные между системами
ai

AI-агент (GigaChat)

  • понимает и структурирует запрос
  • задаёт 3–5 вопросов по существу
  • объясняет ошибки простым языком
  • пишет черновики артефактов
  • ничего не решает и не меняет статусы
  • не выдумывает договоры, ставки, CI
admin

Администратор

  • шаблоны запросов
  • справочники и правила проверки
  • доступы и журналы

Неизменные правила

Пять правил, которые нельзя нарушать

  1. Заказчик не делает работу бэк-офиса

    Договор, ставки, CI, бюджетные коды и этапы спецификации он не вводит и не видит. Это проверяется на уровне API, а не только в интерфейсе.

  2. Решения принимает человек

    Выбор подрядчика, бюджет и отправку на согласование делает исполнитель. AI только рекомендует.

  3. LLM не управляет системой

    Статусы, доступ, расчёты, проверки и рассылки выполняет детерминированный код.

  4. Модель не выдумывает

    Договоры, ставки, CI и бюджет берутся только из КАП и справочников. Если данных нет, система отвечает «не найдено». У каждого вывода есть уверенность и источник.

  5. Всё записывается, ничего не перетирается

    Каждое значимое действие попадает в журнал событий, изменения сохраняются как новые версии. Сбой внешней системы переводит процесс в деградированный режим, но не останавливает его.

Границы

Что входит в MVP

Входит в Этап 1

  • Веб-диалог: текст, файлы, шаблоны
  • Уточнения и ответы по базе знаний процесса
  • Проверка по правилам и договорам КАП, цикл пояснений ошибок
  • Карточка запроса, «Мои заявки», личные шаблоны
  • Рабочее место штаба, варианты подрядчиков
  • Проект спецификации: версии, DOCX, PDF, JSON
  • Решение исполнителя, рассылка на согласование
  • Конфигурационный пакет для ЛК и пакет для трекера

Не входит

  • Голосовой ввод · вне Этапа 1
  • Приём обращений по почте · ждёт решения АР-01
  • Автосоздание Epic/Story · Фаза 2
  • Создание ЗНР через API ЛК · целевой контур
  • Оплата, учёт НМА · целевая АС
  • Автономные решения AI · только отдельным изменением требований

Демо-прототип местами шире MVP: в нём есть голос, автосоздание Epic и создание ЗНР в ЛК. Для требований он не источник.

Как мы работаем

Сначала спецификация, потом код

Каждая фича проходит один и тот же путь. Команды выполняет Claude Code; любой другой ИИ-агент или человек может пройти тот же путь по Markdown-инструкциям из .claude/commands/.

/sber-intent→ /sdd.specify→ /sdd.clarify→ ревью: штаб и техлид→ /sdd.plan→ /sdd.tasks→ /sdd.implement→ /sdd.analyze

spec.md — что и зачем

Сценарии «Дано / Когда / Тогда», требования со ссылками на ТЗ. Без стека и таблиц БД.

plan.md — как

Стек, модель данных, контракты. Каждый план сверяется с 17 статьями конституции.

tasks.md — в каком порядке

Небольшие задачи, тест пишется раньше кода, у каждой задачи есть ссылка на требование.

Не додумывать

Если что-то неясно, ставим [NEEDS CLARIFICATION] в спецификации и добавляем вопрос в общий реестр.
