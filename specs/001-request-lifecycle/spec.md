## 1. Контекст и намерение

Каждая потребность заказчика должна жить как **одна** сущность «Заявка» с понятным для всех участников статусом
(цель Ц4 — прозрачность) и полной, восстанавливаемой историей (Ц5 — аудируемость). Сейчас статусы непрозрачны,
а в источниках существуют три разные статусные модели (Р-1). Эта фича вводит единую каноническую модель
(`docs/domain/request-lifecycle.md`), правила переходов и историю статусов. Она — фундамент Ф1: gate фазы звучит как
«“пустая” заявка проходит жизненный цикл на стенде, всё логируется».

Ключевое ограничение: статусы меняет **только** детерминированная логика по явным действиям (ПР-5, Статьи V, VI, X).

## 2. Пользовательские сценарии

### US-001-1 — Заявка движется по единой статусной модели (P1)

**Как** заказчик и исполнитель **я хочу** видеть, в каком статусе заявка и от кого сейчас ожидается действие,
**чтобы** не выяснять это в переписке.

**Почему P1:** без этого невозможен ни один другой сценарий; это gate Ф1.

**Приёмочные сценарии:**

1. **Дано** заказчик начал диалог, **Когда** система создаёт заявку, **Тогда** заявка получает уникальный номер и статус
   `draft`, владелец шага — заказчик.
2. **Дано** заявка в `awaiting_customer_confirmation`, **Когда** заказчик нажимает «Подтвердить», **Тогда** заявка
   переходит в `request_formed`, затем автоматически в `submitted_to_staff`, владелец шага — очередь штаба.
3. **Дано** заявка в `submitted_to_staff`, **Когда** исполнитель берёт её в работу, **Тогда** статус `staff_review`,
   исполнитель назначен ответственным.
4. **Дано** заявка в `executor_decision`, **Когда** исполнитель выбирает «Отправить на согласование», **Тогда** статус
   `sent_for_approval`, в истории актором указан этот исполнитель.

### US-001-2 — Недопустимый переход невозможен (P1)

**Как** владелец процесса **я хочу**, чтобы система не допускала переходов вне модели, **чтобы** процесс был
предсказуем и юридически значимые шаги нельзя было «перепрыгнуть».

**Приёмочные сценарии:**

1. **Дано** заявка в `staff_review`, **Когда** поступает команда «Отправить на согласование», **Тогда** команда
   отклоняется с причиной «переход staff_review → sent_for_approval не разрешён», статус не меняется, попытка
   фиксируется событием.
2. **Дано** заявка в `executor_decision`, **Когда** команду «Отправить на согласование» инициирует не человек-исполнитель
   (актор `ai` или `system`), **Тогда** команда отклоняется.
3. **Дано** заявка в `awaiting_customer_confirmation`, **Когда** команду «Подтвердить» отправляет пользователь, не
   являющийся заказчиком этой заявки, **Тогда** команда отклоняется (доступ — по 003).
4. **Дано** два пользователя одновременно отправили разные команды по одной заявке, **Когда** первая применена,
   **Тогда** вторая отклоняется как устаревшая и может быть повторена после обновления состояния.

### US-001-3 — История статусов восстанавливается полностью (P1)

**Как** администратор / аудитор **я хочу** по любой заявке увидеть полный путь статусов с актором, временем и
причиной, **чтобы** восстановить историю (ПС-7).

**Приёмочные сценарии:**

1. **Дано** заявка прошла путь от `draft` до `sent_for_approval` с возвратом на уточнение, **Когда** администратор
   открывает историю, **Тогда** видит каждый переход в хронологическом порядке: из какого статуса, в какой, кто
   (тип и id актора), когда, причина/команда.
2. **Дано** любой успешный переход, **Тогда** запись в истории и событие `request_status_changed` появляются вместе
   (нет перехода без записи и записи без перехода).

### US-001-4 — Приостановка, отмена, изменение (P2)

**Как** исполнитель **я хочу** приостановить или отменить заявку, а **как** заказчик — отменить свою заявку на ранней
стадии, **чтобы** отражать реальное состояние потребности.

**Приёмочные сценарии:**

1. **Дано** заявка в активном статусе, **Когда** исполнитель приостанавливает её с указанием причины, **Тогда** статус
   `suspended`, предыдущий статус запомнен; **Когда** исполнитель возобновляет — заявка возвращается в запомненный статус.
2. **Дано** заявка в `draft`…`awaiting_customer_confirmation`, **Когда** заказчик отменяет её, **Тогда** статус
   `cancelled`, действие требует подтверждения и причины (необязательной).
3. **Дано** заявка в `cancelled` или `archived`, **Когда** поступает любая команда изменения, **Тогда** она отклоняется.

### US-001-5 — Срок нахождения в статусе (P2)

**Как** исполнитель **я хочу** видеть, сколько заявка находится в текущем статусе, **чтобы** приоритизировать очередь
(ФТ-2.1) и замечать зависшие заявки (НФТ «Наблюдаемость»).

**Приёмочные сценарии:**

1. **Дано** заявка перешла в `submitted_to_staff` 3 часа назад, **Когда** исполнитель смотрит очередь (030), **Тогда**
   доступно значение «в статусе 3 ч».

### Граничные случаи и ошибки

- **GigaChat недоступен во время `ai_intake`** (Статья XI): заявка не попадает в «ошибочный» статус. Система
  сохраняет ввод, возвращает заявку в `draft` с пометкой о деградации; заказчику доступны шаблонный путь и передача
  на ручную обработку штабу (см. FR-001-14).
- **AI вернул невалидный ответ** (Статья VII): трактуется как сбой анализа — тот же путь, что и недоступность.
- **Система-источник события недоступна (журнал событий)**: переход не применяется без записи события (атомарность),
  команда возвращает ошибку «повторите позже». [Детали — в плане 002.]
- **Внешний результат согласования/ЗНР** в MVP не поступает автоматически: соответствующие переходы выполняет
  исполнитель вручную (Этапы, задача 5.4).

### Ключевые сущности

- **Заявка (`Request`)** — номер, текущий статус, предыдущий статус (для `suspended`), момент входа в статус, заказчик,
  назначенный исполнитель, признак «без AI-анализа».
- **Запись истории статусов (`StatusHistory`)** — из, в, команда, тип и id актора, причина, время.
- **Таблица переходов (`TransitionTable`)** — декларативный перечень строк «из / команда / актор / в / условия».

### Порождаемые события

- `request_created` — при создании (актор — заказчик); payload: номер, канал.
- `request_status_changed` — при каждом успешном переходе; payload: from, to, команда, причина.
- `request_transition_rejected` — при отклонённой команде; payload: текущий статус, команда, актор, код причины.
  *(новый тип — добавлен в `docs/domain/events.md`)*
- `request_cancelled`, `request_suspended`, `request_archived` — специализированные события поверх `request_status_changed`.

### Применимые НФТ

| НФТ | Значение для этой фичи |
|---|---|
| Производительность | Применение команды перехода — в пределах бюджета справочных операций API (≤ 200 мс p95) |
| Надёжность | Нет потерянных или «половинчатых» переходов при сбоях (атомарность FR-001-05) |
| Аудируемость | Полный путь статусов любой заявки восстанавливается (ПС-7) |
| Наблюдаемость | Метрики: распределение заявок по статусам, время в статусе, «зависшие» заявки |

## 4. Вне скоупа

- Интерфейсы очереди, карточки, «Моих заявок» (013–015, 030) — здесь только данные и правила.
- Уведомления о смене статуса (036) — подписываются на `request_status_changed`.
- Инфраструктура журнала событий (002) — здесь только какие события публикуются.
- Автоматическое получение статусов из ЛК / систем согласования (040, Этап 2).
- Версионирование карточки и спецификации как таковое (014, 034) — здесь только требование сохранять версии при возвратах.

## 5. Критерии успеха

- **SC-001-1:** Табличные тесты покрывают все пары «статус × команда × актор»; 100% пар вне таблицы отклоняются, 100% пар
  из таблицы применяются.
- **SC-001-2:** Для 100% заявок на стенде путь статусов, восстановленный из истории, совпадает с последовательностью
  событий `request_status_changed` (основа ПС-7).
- **SC-001-3:** Gate Ф1: «пустая» заявка проходит путь `draft → … → completed → archived` на стенде через API
  с записью всех событий.
- **SC-001-4:** Ни один переход в `sent_for_approval` в журнале не имеет актора, отличного от человека-исполнителя.
