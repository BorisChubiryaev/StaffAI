# Конституция проекта StaffAI

**Версия:** 1.0.0 · **Действует с:** 2026-10-15 · **Подтверждение:** на согласительной сессии Ф0 (задача 0.1)

Конституция — набор неизменяемых по умолчанию принципов, которым подчиняются все спецификации, планы и код.
Каждая статья сформулирована так, чтобы её можно было **проверить** при ревью плана (`/sdd.plan` → «Проверка конституции»)
и кода. Принципы выведены из ТЗ v3, Видения и Замечаний; ссылки — в скобках.

---

## Часть A. Продукт

### Статья I. Цель — специалисты в команде, а не документ
Ценность измеряется скоростью и прозрачностью вывода специалистов. Спецификация, ЗНР, пакет для трекера — downstream-артефакты,
которые система генерирует из уже собранных данных. *(ТЗ v2 §0.2, Замечания §1)*
- **Проверка:** спецификация фичи формулирует пользу через путь заявки/метрики процесса, а не через «форму документа».

### Статья II. Заказчик — не оператор бэк-офиса
Заказчик не вводит и не видит: номер договора, ставки, CI, бюджетные коды и контур, продукт ЕК, стратегическую тему,
этапы спецификации, подписантов подрядчика, служебные данные AI (уверенность, источники, сопоставления). *(ФТ-1.7, ПС-4)*
- **Проверка:** в контрактах API, доступных роли `customer`, этих полей нет (тест на уровне API, а не только UI).
- Заказчик может *высказать пожелание* по подрядчику — это свободный текст, не выбор договора.

### Статья III. Один ввод — многократное использование
Данные вводятся один раз и переиспользуются в карточке, спецификации, пакетах для ЛК и трекера, коммуникации.
Ни один экран не просит пользователя повторно ввести то, что система уже знает. *(Ц2, ПС-1, ПС-4)*
- **Проверка:** для каждого поля ввода в спецификации указан источник; поле, которое можно вывести из имеющихся данных, — не ввод.

### Статья IV. Критический путь без искусственных блокеров
Обработку блокирует только минимум (кто заказчик, какие роли и сколько, ориентировочные сроки, контекст). Всё остальное
уточняется к тому шагу, где реально нужно. Противоречия подсвечиваются, но не блокируют. *(ts-v2 §5.0.1, ФТ-3.4)*
- **Проверка:** каждое обязательное поле в спецификации помечено шагом процесса, к которому оно обязательно.

## Часть B. AI

### Статья V. Решение — за человеком
Система не принимает самостоятельно решений о выборе подрядчика, утверждении бюджета, отправке на согласование и любых
юридически значимых действиях. Перевод решения в автоматический режим — только отдельным изменением требований на
основе метрик эксплуатации. *(ТЗ §4, схема агента)*
- **Проверка:** каждое такое действие — явная команда пользователя-человека с записью актора в журнале.

### Статья VI. Детерминированное ядро, LLM на периферии
LLM не используется для статусных переходов, контроля доступа, расчётов, валидации по справочникам и договорам,
рассылок и уведомлений. Модели не предоставляются инструменты для этих действий. Её ответ — рекомендация. *(ПР-5, ADR-0002)*
- **Проверка:** в плане для каждой функции указано «LLM / алгоритм / hybrid»; LLM-вызовы не имеют побочных эффектов,
  кроме записи `AiInference`.

### Статья VII. Достоверность и объяснимость AI
1. Каждый AI-вывод имеет уверенность и источник; факт / справочное значение / предположение разделены. *(ПР-1, ПР-2)*
2. Договоры, ставки, CI, бюджеты **никогда не генерируются** моделью — только из КАП и справочников; иначе «не найдено»,
   при неоднозначности — варианты. *(ПР-3)*
3. Выводы ниже порога уверенности направляются на проверку исполнителю.
4. Ответы модели проходят валидацию по JSON-контракту; невалидный ответ — ошибка, а не данные. *(ФТ-3.8)*
5. Промпты версионируются в репозитории; изменение промпта сопровождается прогоном eval на эталонном наборе. *(Ф2, 2.10)*
- **Проверка:** в плане есть раздел «AI: контракт, промпты, eval»; eval-тесты в CI.

### Статья VIII. Данные банка остаются в контуре банка
Реальные данные заявок, договоров, ставок и персональные данные обрабатываются только в контуре банка и только
разрешённой моделью (GigaChat, ИВ-1). В репозиторий, тестовые фикстуры, промпты внешних ИИ-ассистентов и логи CI
попадают только синтетические или обезличенные данные. Секреты не хранятся в репозитории. *(НФТ «Безопасность», ТУ-10)*

## Часть C. Система

### Статья IX. Аудит by design
Каждое значимое действие (человека, AI, системы) — событие журнала по единому контракту (id, заявка, актор, время,
payload, корреляция, источник). Исходный ввод неизменяем и хранится отдельно; всё, что меняется после подтверждения, —
новая версия с автором и временем. По журналу восстанавливается полная история любой заявки. *(ФТ-6.3, ФТ-2.7, ФТ-5.2, ПС-7)*
- **Проверка:** спецификация перечисляет порождаемые события; новые типы добавлены в `docs/domain/events.md`.

### Статья X. Единый жизненный цикл
Одна потребность — одна сущность «Заявка» с общей статусной моделью (`docs/domain/request-lifecycle.md`). Переходы
выполняет только детерминированная машина состояний; недопустимый переход отклоняется. *(ФТ-6.1)*

### Статья XI. Интеграции через адаптеры, деградация вместо отказа
Каждая внешняя система — за адаптером с режимами `mock` / `read_only` / `read_write`, переключаемыми конфигурацией.
Недоступность GigaChat или внешней системы не останавливает процесс: отложенная синхронизация, ограниченный режим,
локальное сохранение. Система не является источником истины для справочных и договорных данных. *(ФТ-6.4, §7.1, НФТ)*
- **Проверка:** план описывает поведение фичи при недоступности каждой зависимости; есть тест на режим отказа.

### Статья XII. Ролевая видимость на уровне сервера
Заказчик видит только свои заявки, исполнитель — очередь и назначенные, администратор — всё. Ограничения применяются
на сервере; UI лишь отражает их. *(ФТ-6.2)*

## Часть D. Процесс разработки

### Статья XIII. Сначала спецификация
Код фичи пишется только по спецификации со статусом не ниже `Approved` и плану, прошедшему проверку конституции.
Исключения: исправление дефектов, рефакторинг без изменения поведения, инфраструктурные chores. *(ADR-0001)*

### Статья XIV. Не додумывать — спрашивать
Неясности и неподтверждённые сведения (пометки АР/ТУ в ТЗ) не реализуются как факт: они помечаются
`[NEEDS CLARIFICATION: …]` и заносятся в `docs/open-questions.md`. Спецификация с открытыми блокирующими вопросами
не может получить статус `Approved`.

### Статья XV. Трассируемость
Каждое требование спецификации ссылается на источник (ФТ/ПР/ИВ/ПС ТЗ или иной документ из иерархии); каждая задача —
на требование или сценарий спецификации; каждый приёмочный сценарий — на тест. *(docs/requirements/traceability.md)*

### Статья XVI. Тесты до реализации
Для каждого пользовательского сценария сначала пишутся приёмочные тесты (Дано/Когда/Тогда), затем код. Детерминированное
ядро покрывается модульными тестами; интеграции — контрактными тестами против `mock`-адаптеров; AI — eval-набором.

### Статья XVII. Простота
Предпочитаем минимальное решение, закрывающее спецификацию. Новый сервис, фреймворк или слой абстракции требует
обоснования в плане («Отклонённые альтернативы») и, если решение дорого отменить, — ADR.

## Управление конституцией

- Изменение статьи = PR с ADR, обоснованием и обновлением версии (SemVer: MAJOR — удаление/смягчение принципа,
  MINOR — новая статья, PATCH — уточнение формулировок).
- Отклонение от статьи в конкретном плане допускается только с явной записью в разделе «Обоснованные отклонения»
  плана и согласием техлида; повторяющиеся отклонения — сигнал к изменению конституции.
- При противоречии между конституцией и любым другим документом проекта действует конституция; противоречие с ТЗ v3 —
  повод для открытого вопроса, а не для молчаливого выбора.
